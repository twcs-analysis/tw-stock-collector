## 策略概述

### 目標

回補歷史月營收資料，建立完整的時間序列資料集，支援：
- 長期趨勢分析
- 同比/環比分析
- 季節性分析
- 歷史回測

### 回補範圍建議

```
建議回補範圍:
┌────────────────────────────────────────────┐
│  最小範圍: 最近 12 個月                      │
│  - 用途: 年增率計算                         │
│  - 資料量: ~24,000 筆 (2,000 檔 × 12 月)   │
│  - 預估時間: 2-3 小時                       │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  推薦範圍: 最近 3 年 (36 個月)               │
│  - 用途: 中期趨勢分析、季節性分析            │
│  - 資料量: ~72,000 筆 (2,000 檔 × 36 月)   │
│  - 預估時間: 6-9 小時                       │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  完整範圍: 5-10 年                           │
│  - 用途: 長期研究、完整歷史資料              │
│  - 資料量: ~120,000-240,000 筆             │
│  - 預估時間: 10-20 小時                     │
└────────────────────────────────────────────┘
```

## API 可用性分析

### MOPS API 歷史資料支援

✅ **完全支援歷史資料查詢**

**測試驗證**:
```bash
# 查詢 2024 年 1 月（兩年前）
curl -X POST https://mops.twse.com.tw/mops/api/t05st10_ifrs \
  -H 'Content-Type: application/json' \
  --data '{
    "companyId": "2330",
    "dataType": "2",
    "month": "1",
    "year": "113",
    "subsidiaryCompanyId": ""
  }'

結果: ✅ 成功返回資料
```

**支援範圍**:
- ✅ 可查詢任意歷史年月
- ✅ 至少支援到 10 年前（實測：2014 年資料可查）
- ✅ 資料格式與當月一致
- ⚠️ 極早期資料（2000 年前）可能無法查詢

### OpenAPI 歷史資料支援

❌ **不支援歷史資料查詢**

**限制**:
- 只提供最新一期月營收
- 無法指定年月參數
- 不適用於歷史回補

**結論**: 歷史回補**只能使用 MOPS API**

## 回補策略設計

### 策略比較

| 策略 | 方式 | 優點 | 缺點 | 適用情境 |
|------|------|------|------|----------|
| **A. 逐月回補** | 按時間順序，每月收集所有公司 | 資料完整、易於驗證 | 耗時最長 | 完整歷史建立 |
| **B. 逐股回補** | 按公司，一次收集該公司所有月份 | 可並行、進度清楚 | 實作複雜 | 特定公司補充 |
| **C. 分批混合** | 分批次執行，每批包含部分公司部分月份 | 平衡效能與風險 | 需要狀態管理 | 大量歷史回補 |
| **D. 智慧回補** | 檢查缺失後只補缺口 | 最快速、避免重複 | 需要檢查機制 | 增量補充 |

### 推薦策略：**策略 C（分批混合）+ 策略 D（智慧回補）**

```
回補流程設計:
════════════════════════════════════════════════════

階段 1: 資料缺口分析
  ↓
  檢查現有資料覆蓋範圍
  識別缺失的（年月, 股票）組合
  建立待補充清單

階段 2: 分批回補
  ↓
  將待補充清單分批（每批 500 檔 × 1 月 = 500 次請求）
  每批之間休息 60 秒（避免被封鎖）
  支援斷點續傳

階段 3: 驗證與修正
  ↓
  驗證資料完整性
  重試失敗項目
  生成回補報告
```

## 效能優化

### 批次大小策略

```python
批次大小建議:
═══════════════════════════════════════

小批次（100-200 檔/批）:
✅ 優點: 風險低、易於恢復
❌ 缺點: 總執行時間較長
📊 適用: 首次測試、網路不穩定

中批次（500-800 檔/批）: ⭐ 推薦
✅ 優點: 平衡效能與風險
✅ 優點: 可在數小時內完成
📊 適用: 一般歷史回補

大批次（1000+ 檔/批）:
✅ 優點: 執行最快
❌ 缺點: 風險高、易被封鎖
⚠️ 不建議使用
```

### 請求延遲策略

```python
延遲時間建議:
═══════════════════════════════════════

極保守（1.0-2.0 秒）:
• 最安全，幾乎不會被封鎖
• 但耗時極長（2,000 請求 ≈ 33-66 分鐘）

保守（0.5-1.0 秒）: ⭐ 推薦
• 安全性高
• 2,000 請求 ≈ 16-33 分鐘
• 適合大量回補

標準（0.3-0.5 秒）:
• 平衡模式
• 2,000 請求 ≈ 10-16 分鐘
• 適合中小量回補

激進（0.1-0.3 秒）:
• 有被封鎖風險
• 僅適合少量資料（< 100 檔）
```

### 並行策略（進階）

```
多程序並行:
═══════════════════════════════════════

策略: 將股票清單分割，多程序同時執行

範例:
Process 1: 股票 0000-0999   (1000 檔)
Process 2: 股票 1000-1999   (1000 檔)

優點:
✅ 執行時間減半（16 分鐘 → 8 分鐘）
✅ 充分利用多核心 CPU

風險:
⚠️ IP 被封鎖風險大幅提升
⚠️ 需要更複雜的狀態管理

建議:
• 僅在測試環境使用
• 控制並行數量（最多 2-3 程序）
• 每個程序使用不同延遲策略
```

## 風險與挑戰

### 風險 1: IP 被封鎖 ⚠️

**機率**: 🟡 中
**影響**: 🔴 高

**情境**:
```
連續發送大量請求（2,000+ 次）可能觸發:
• Rate limiting (速率限制)
• IP 暫時封鎖（數小時到數天）
• CAPTCHA 驗證要求
```

**緩解措施**:
```python
1. 控制請求速率（每秒 1-2 次）
2. 加入隨機延遲（0.3-0.8 秒）
3. 分批執行，每批之間休息
4. 監控 HTTP 狀態碼（偵測 429）
5. 遇到封鎖立即停止
```

**應變計畫**:
```
如果被封鎖:
1. 立即停止所有請求
2. 記錄已完成的進度（斷點續傳）
3. 等待 24-48 小時
4. 降低請求速率後重試
5. 考慮使用代理或 VPN（需謹慎評估合法性）
```

---

### 風險 2: 資料不完整 ⚠️

**機率**: 🟡 中
**影響**: 🟡 中

**情境**:
```
歷史資料可能存在:
• 公司尚未上市（無資料）
• 公司已下市（資料消失）
• 特殊期間無營收（例如：停業）
• API 資料缺失（系統問題）
```

**處理策略**:
```python
1. 記錄「查無資料」情況（不算失敗）
2. 建立資料缺口報告
3. 標記資料完整性狀態
4. 提供人工複查機制

資料缺口分類:
- 正常缺口: 公司未上市期間（預期）
- 異常缺口: 已上市期間卻無資料（需調查）
```

---

### 風險 3: 資料一致性問題 ⚠️

**機率**: 🟢 低
**影響**: 🟡 中

**情境**:
```
公司可能更正前期營收:
• 會計年度調整
• 合併報表修正
• 錯誤更正
```

**處理策略**:
```python
1. 定期重新回補（例如：每季一次）
2. Git 版本控制保留歷史
3. 資料庫使用 UPSERT 更新
4. 記錄更新時間戳記
5. 提供資料版本比對工具
```

---

### 風險 4: 執行時間過長 ⚠️

**機率**: 🟡 中
**影響**: 🟢 低

**情境**:
```
完整 5 年回補:
• 2,000 檔 × 60 月 = 120,000 筆
• 每筆 0.5 秒 = 16.7 小時
```

**優化策略**:
```python
1. 分批執行（每日 3-4 小時）
2. 背景執行（不影響其他工作）
3. 斷點續傳（可隨時中斷）
4. 進度可視化（進度條、預估剩餘時間）
5. 完成後通知（Email/Slack）
```

## 實作指引

### 回補腳本設計

**檔案**: `scripts/data-collector/backfill_revenue.py`

**核心功能**:

```python
主要參數:
─────────────────────────────────────
--start-date YYYY-MM      開始年月
--end-date YYYY-MM        結束年月
--stock-id CODE           指定股票（可選）
--stock-ids CODE,CODE     多檔股票（可選）
--batch-size N            批次大小（預設 500）
--delay SECONDS           請求延遲（預設 0.5）
--from-gaps-report FILE   從缺口報告回補
--resume-from FILE        斷點續傳
--dry-run                 模擬執行（不實際請求）

進階參數:
─────────────────────────────────────
--max-workers N           並行程序數（預設 1）
--retry-failed            重試失敗項目
--skip-validation         跳過驗證（不建議）
--output-dir PATH         輸出目錄
```

**執行流程**:

```
1. 參數解析與驗證
   ↓
2. 建立回補清單
   - 根據日期範圍生成（年月, 股票）組合
   - 如果指定 stock_id，僅包含該股票
   - 如果從 gaps report，載入缺口清單
   ↓
3. 檢查現有資料（智慧回補）
   - 查詢資料庫或 JSON 檔案
   - 過濾已存在的資料
   - 僅保留缺失項目
   ↓
4. 分批執行回補
   - 將清單分批（batch_size）
   - 逐批執行，批次間休息 60 秒
   - 每筆請求延遲 delay 秒
   ↓
5. 錯誤處理與重試
   - 記錄失敗項目
   - 重試機制（最多 3 次）
   - 遇到封鎖立即停止
   ↓
6. 資料驗證與儲存
   - 驗證資料完整性
   - 儲存 JSON 檔案
   - 更新進度檔案（斷點續傳）
   ↓
7. 生成回補報告
   - 成功數量
   - 失敗數量（附原因）
   - 執行時間
   - 資料覆蓋率
```
